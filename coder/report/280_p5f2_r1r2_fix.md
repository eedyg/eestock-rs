## 2. 问题与修复

### R1（根因，necessary condition）——`specPanes` memo 依赖缺卫星高度

**缺陷**：`specPanes = useMemo(..., [basePeriod, baseHeight, periodsKey])` 只按「卫星**周期列表**」（`periodsKey`）比对。
父层（`DashboardPage.saveMultiPeriodHeights`）的**成功回显/失败回滚只改卫星高度**（基准请求值不变）时，该 memo 不重算
⇒ 组件继续沿用**旧卫星请求** ⇒ 拖拽在回执 settle 后回弹、屏幕与服务端配置分叉
（P5 验收实测 600px：拖中 `{294,112,82,112}` → 回执后 `{294,97,97,112}`，差 15px）。

**修复（稳定签名）**：

```ts
const satelliteHeightsKey = satellites.map((s) => `${s.period}:${s.height}`).join('\u0000');
const specPanes = useMemo(/* … */, [basePeriod, baseHeight, periodsKey, satelliteHeightsKey]);
```

为什么用**串签名**而不是把 `satellites` 数组直接入依赖：该数组每次渲染都是**新引用**（页面侧 `SATS.map(...)`）⇒
入依赖会让 memo 每渲染重算（无谓重算 + `layout`/`paneHeights` 级联重算）。`周期:高度` 规范化串**同值 ⇒ 同串 ⇒ 不重算**，
只有真实高度/周期变化才重算；`periodsKey` 保留（可读性；其信息被子集包含）。这是 R1 判据（memo 必须把**卫星高度**列入依赖）的落地形式。
连带效果：`requestSig = specPanes.map(p => String(p.requested)).join('|')` 也随之感知卫星高度 ⇒ 「回执到达即丢弃本地拖拽期望」的既有机制（§6.3 权威交还）对**只改卫星高度**的回执同样生效。

### R2——拖拽基线改为**载荷域内的当前值**

**缺陷**：`beginDrag` 里 `const seed = paneHeights`（**屏幕分配值**）。越域（`fit` 路径基准吸收余量 ⇒ 屏幕基准可 > `HEIGHT_MAX=1200`）时，
屏幕值与持久化口径（`payload == clamp(分配)`）相差 ≤61px；以屏幕值为基线会让下一次拖拽的起点与已持久化值错位
⇒ 出现「拖了载荷不变」（死区）与「真实服务端值重载后跳变 20px」。

**修复**：

```ts
// 裁决 ①：基线 = 持久化域内的当前值（clamp(当前分配)），不是屏幕分配值。
// 仍保留 B6 口径：基线取「当前」而非上次拖拽的原始期望值。
const seed = toPersistableHeights(paneHeights);
```

`toPersistableHeights` 是既有唯一载荷出口函数（逐项 `round` + 夹到 `[80,1200]`，与 `crates/web/src/dto.rs` 第 5 条同域），
直接复用即可，**未新增函数/依赖/模块**。裁决 ② 保持不变：`fit` 模式下基准 = **余量吸收项**（屏幕高 = 可用 − Σ卫星），其持久化值仅作记录；
裁决 ① 与裁决 ② 的并列结果是：每次拖拽都**单调改载荷**（无死区），屏幕由分配算法决定，二者 ≤61px 偏差属**已知且允许**。

> 诚实说明（与 tester 探针结论一致）：由于 `fit` 路径下基准请求值**不参与**分配（基准 = 可用 − Σ卫星），
> 裁决 ① 在本分配算法下**几乎不可观测**（δ ∈ [−200, +1200] 时分配/载荷逐值相同）。
> 它**不是**本轮判据转绿的杠杆（杠杆是 R1）；实现它是为满足契约 ① 并在算法演进时保持拖拽语义不变。

### 载荷 / 分配口径（两条硬口径，未变）

- 载荷：`onHeightsChange(toPersistableHeights(paneHeights))` ⇒ 每项 ∈ `[80,1200]` 整数；
- 渲染分配：可越域（`fit` 基准可 > 1200）且恒 `Σ == 可用高度`（或 `min-overflow` 退化可滚动且可观测）；**不为凑域而夹分配**。

## 4. R1-G3 期望值修正（Tester 资产，Supervisor 显式授权；修正算术错误 + 加强判据）

**原断言为什么必然假红**：探针 `setHeights({1h:112, 5m:82})` 是**合并**进父层当前 props（= 两次拖拽后的载荷 `{15m:294,1h:112,5m:92,1d:102}`），
请求变 `{15m:294,1h:112,5m:82,1d:102}` ⇒ **Σ请求 = 590 < 可用 600**。
按 §6.1「D ≤ H ⇒ 按配置 px 直用，余量由分配算法吸收」+ 裁决 ②（`fit` 基准 = 可用 − Σ卫星），正确分配 = `{15m:600−296=304, 1h:112, 5m:82, 1d:102}`。
原期望 `{...before, '1h':112, '5m':82}` = `{294,112,82,102}` 把「**旧屏幕基准 294**」与「**新卫星回执**」混在一起
⇒ 该断言只有在 `setHeights` 恰好保持 Σ=600 时才自洽，**任何满足 §6.1 的实现在此都必然 FAIL**（旧断言即此算术错误）。

**修正与加强**（`diff_p5f2_harness_r1g3.patch`）：

- 期望值改由**请求值**推导（不取自 `after`，避免自我循环）：`expectedSats = {1h:112, 5m:82, 1d: before['1d']=102}`；
  `expectedBase = 600 − (112+82+102) = 304`；`expectAdopted = {15m:304, 1h:112, 5m:82, 1d:102}`；
- 断言加强为**三条并列**（⊇ 原强度）：① `satsAdopted`（卫星逐值采用回执 —— 「memo 依赖已修」的核心判据）∧
  ② `baseAbsorbs`（基准 == 可用 − Σ卫星 —— 余量吸收规则的显式断言）∧ ③ `sumEqualsAvailable`（Σ分配 == 600）；
- 断言旁写入上述推导注释，并显式声明「**不得**写成基准沿用旧屏幕值」（防后续读者改回错误期望）。

**判定**：这是**修正算术错误并加强判据，非放宽** —— 变异审计（§3.1）证明回退 R1 修复后该断言**仍会变红**。
