## 判词（结论）

**① 生产真路径每 run 的进度 UPDATE = 1001 帧，全部落到 DB；不存在背压、合并或丢弃。**

单次受控 run（真路径 REST 提交，`sr_1789663588369_000007`，M5 3500 bar，dur 3.459 s）实测：

```

理论: min(1001, bars) 进度帧 + mark_started(1) + mark_succeeded(1) = 1001 + 2 = 1003
⇒ 1003 == 1003 精确闭合；终态后 240 s 采样 120 次无任何后续增量 ⇒ 无「迟到」的帧（该 run 每帧 3.45 ms）。
```

三档规模（bar 数跨 4.6×）实测 `dur` 与 `1003 × 每帧写库耗时` 一致：

| 档 | bars | 理论帧 = min(1001,n)+2 | 实测 dur_s | dur/理论帧 |

⇒ **`dur` 与 bars 无关、与帧数（≤1003，封顶）成正比**：bar 数 4.6× 而 `dur` 相同（2.59 vs 2.58 s）。
⇒ 当前每帧写库 ~2.6 ms（`synchronous_commit=on`/`fsync=on`/`wal_sync_method=fdatasync`）。

**推翻项**：ADR §2.6/D15 原文「生产必然存在背压/合并/丢弃」（依据：副本 1001 帧 × 3.3 ms = 3.3 s > 真 run median 0.854 s）
**不成立**。真路径 1001 帧**全部**写库。0.854 s 的正确解释是**当时每帧写库 ≈ 0.85 ms**（历史样本内部一致：bars=29 → dur 0.026 s ⇒ 31 帧 × 0.84 ms），
即 `dur ≈ 每帧 fsync 延迟 × 1003`，延迟随主机 I/O 在 0.85–3.3 ms 间浮动；**帧数恒定 1003**。

## ③ 测量方法学（必须随结论一起引用的修正）

PG15+ 表级统计由**该后端**按最小间隔才 flush（实测：run 终态后计数仍会「迟到」+13/+22/+64/+79）。
⇒ v2「run 后 settle 4×0.5s」协议的 Δ **不可用**（T1 472/T4 497/T2 940/T3 1065 均被前后 run 的迟到尾数污染，与被污染项不闭合）。
