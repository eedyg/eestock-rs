## 1. ① 每 run 的进度 UPDATE 次数 —— 真路径直接测量（免改代码）

### 1.1 方法
1. 通过现网 REST（`POST http://127.0.0.1:8081/api/workbench/runs`）提交**单次受控 run**（= 生产真路径，与用户提交同进程同库）。
2. 围绕该 run 取 `pg_stat_user_tables.strategy_run.n_tup_upd` **差值**（另取 `pg_stat_database.tup_updated` 交叉核对）。
3. 同窗口并发度用 `strategy_run.started_at/finished_at` **区间交集**判定；提交前后各查 `status IN ('queued','running')` 计数。
4. 理论值：进度帧 = **min(1001, bars)**（`workbench.rs:814` `milli=(progress*1000) as i64`、`last_milli=-1` ⇒ 帧数 = 进度 0.1% 档位数），succeeded run 另有 **2** 次状态迁移 UPDATE（`mark_started` + `mark_succeeded`；全部 `UPDATE strategy_run` 位置仅 5 处，见 `struct_sql.txt`）。

### 1.2 测量学修正（本轮必须先讲，否则数字会被误读）
PG15+ 的表级统计由**该后端**按最小间隔才 flush 一次。实测：run 终态后计数仍会「迟到」`+13 / +22 / +64 / +79`。
⇒ **v2「settle 4×0.5 s」协议的 Δ 不可用**（前一条 run 的尾数被计入后一条）：见表 A 第 4–7 行（472 / 497 / 940 / 1065）。
⇒ **可用协议 = 长窗口**：前置 **90 s** idle guard（每 2 s 采样 × 45 次，确认零漂移）+ 后置 **240 s** 采样 × 120 次（确认零漂移）。

### 1.3 结果（表 A 第 8 行，唯一「可用」点）

```
[PRE ] 2026-09-17T16:46:28.336Z  n_tup_upd = 363038   （前置 90 s guard 45 次采样全部 = 363038，Δ0）
提交  POST /api/workbench/runs  → 201  run_id = sr_1789663588369_000007  (M5 159740, 3500 bar, warmup 250)
[TERM] 2026-09-17T16:46:31.908Z  status=succeeded   dur_s = 3.459
[POST] 2026-09-17T16:50:36.396Z  n_tup_upd = 364041   （后置 240 s / 120 次采样全部 = 364041）
Δ = 1003        理论 = min(1001,3500) + mark_started(1) + mark_succeeded(1) = 1001 + 2 = 1003
overlapping_other_runs = 0
```

### 1.4 规模对照（真路径 `dur`，`per_run_table.md` 表 A）

| 档 | bars（= 引擎循环 n = per_bar 长度，含 250 warmup） | 理论帧 = min(1001,n)+2 | 实测 dur_s | dur/帧 |
|---|---|---|---|---|
| 小 D1 | 492 | 494 | 1.305 | 2.64 ms |
| 中 M5 | 3500 | 1003 | 2.592 | 2.58 ms |
| 大 M1（≈93 天上限） | 16155 | 1003 | 2.578 | 2.57 ms |

**bars ×32.8（492 → 16155）而 `dur` ×0.98**；3500 与 16155 两档几乎相同（2.592 / 2.578 s）
⇒ `dur` 由**帧数封顶 1001** 决定，与 bars 无关。这是「每 run 固定开销」在**真路径**上的直接实测。

### 1.5 与 ADR §2.6「生产必然存在背压/合并/丢弃」的关系（**推翻**）

架构师推断链：副本 1001 帧 × 3.3 ms = 3.3 s，而真 run median 仅 0.854 s ⇒ 必有丢弃/合并。
**实测否决该推断**：1001 帧**全部**写库（Δ 精确 = 1003）。
真 run median 0.854 s 的**正确解释**：**当时每帧写库 ≈ 0.85 ms**——历史样本内部自洽（bars=29 的 run `dur=0.026 s` ⇒ 31 帧 × 0.84 ms；`dur/(min(1001,bars)+2)` 中位 = **0.862 ms/帧**，p10 0.837 / p90 1.723）。
⇒ **变量是「每帧 fsync 延迟」（0.85 → 3.45 ms，随主机 I/O 浮动），不变量是「帧数 1003」。**

## 2. ② pg 侧结构证据（只读）

### 2.1 累计 UPDATE 与状态迁移的量级差（独立复核架构师数字）

`raw.txt §[3]` / `queries.sql`：

```sql
SELECT relname,n_tup_ins,n_tup_upd,n_tup_del,n_tup_hot_upd,n_live_tup FROM pg_stat_user_tables
WHERE relname IN ('strategy_run','strategy_run_result');
--  strategy_run        | 2349 | 357386 | 1976 | 329852 | 374
--  strategy_run_result | 1473 |      0 | 1100 |      0 | 374
```

- **数字复核一致：`n_tup_upd = 357,386`**（且 idle 15 s 前后 Δ=0 ⇒ 无其它写入者；`n_tup_ins=2349 ≈` 存活 374 + 历史删除 1976 ⇒ **统计覆盖全表历史、未被 reset**）。
- **状态迁移点计数（代码结构，不做根因推断）**：`grep -n "UPDATE strategy_run" crates/storage/src/workbench.rs` ⇒ 恰好 5 处：
  `:107 mark_started`（queued→running）、`:116 update_progress`（进度帧，N/run）、`:131 mark_succeeded`、`:152 mark_failed`、`:169 mark_canceled`。
  ⇒ succeeded run 的状态迁移 UPDATE = **2**；`strategy_run_result` 从不被 UPDATE（`n_tup_upd=0`，交叉印证）。
- **pg 写路径参数**：`synchronous_commit=on`、`fsync=on`、`wal_sync_method=fdatasync`（另 `wal_level=replica`、`max_wal_size=1GB`）—— 与 ADR §2.6 一致。

### 2.2 算术闭合（回答「357,386 ÷ 374 ≈ 955/run」与「~150/run」）

对 374 条存活 succeeded run 用 `per_bar` 长度算理论帧：

```
Σ (min(1001, bars_i) + 2) over 374 runs = 346,441   （占累计 357,386 的 96.9%）
残差 = 10,945（3.1%）⇒ 属于 1,976 条**已被删除**的 run（多为 queued→failed/canceled：只有 1 次状态迁移、无进度帧）
```

- **「~150/run」错在哪**：`357,386 ÷ 2,349` 把分子（含被删 run 的更新）除以**历史插入总数**（2,349，其中 1,976 行是**已被删除的轻量测试 run**，不是完整 run）。分母取错 ⇒ 每 run 成本被低估 **~6.7×**。
- **「÷374 ≈ 955/run」也不可当 per-run 成本**：分母只含存活 run、分子含被删 run，且各 run bar 数不同（帧数在 1001 处封顶 ⇒ 均值被小 run 拉低）。
- **正确的 per-run 口径（实测）**：**1003 次/run**（完整规模 run；小 run 为 `min(1001,bars)+2`）。
- 残余不确定性（如实标注）：1,976 条被删 run 的 bar 数已不可查，故「残差 10,945 归因于被删 run」是**闭合一致性推断**（若被删 run 规模与存活 run 相当，累计应为 ~2.2M ≈ 观测的 6 倍，反证它们**大多是轻量/失败 run**）。

## 4. ④ 结构性事实：进度帧是否可能被丢弃/合并（**只报结构事实，不下根因结论**）

`crates/application/src/workbench.rs`（`struct_sql.txt` 原样摘录，行号）：

| 结构事实 | 位置 |
|---|---|
| 通道类型 = `tokio::sync::mpsc::unbounded_channel::<(f64, DateTime<Utc>)>()` —— **无界、无容量上限** | `:778` |
| 发送端只有 `tx.send(...)`，**没有 `try_send`**、**没有 `send_timeout`**、**没有 drop/丢弃分支**（`let _ =` 只丢弃 SendError，即接收端已关闭） | `:822` |
| 报告任务 `tokio::spawn` 串行 `while let Some(...) = rx.recv()`，每帧顺序执行 `sink.send(...).await` 后 `store2.update_progress(...).await`（**每帧一次同步 UPDATE**） | `:782-787` |
| 引擎结束（含 Break）后 **drop 发送端 → `report_task.await` 排空**（注释自述「进度/落库完成，确定可复现」） | `:826-827` |
| 节流条件：`milli = (progress*1000) as i64`（`PROGRESS_THROTTLE_MILLI = 1000.0`），仅当 `milli != last_milli || i+1 == total` 才 `tx.send` ⇒ 产出帧数 = `min(1001, n)` | `:58, :814-820` |
| 背压语义：**无界通道 + 串行 drain + 结束前 await 排空** ⇒ 结构上**不存在**容量型丢弃路径；`send` 不施加反向压力给引擎线程 | 同上 |

**测量一致性**：结构上的「无丢弃路径」与 §1.3 的 Δ=1003 精确闭合一致（测量与代码结构互为独立证据）。
（按纪律：**不在此下「为什么 dur 是 0.85 ms 还是 3.45 ms」的根因结论** —— 这需要 P4b 的 span/计数器仪表。）

## 6. 纪律与残留风险

**已遵守**：不改生产代码；不 commit；代码阅读仅用于「结构事实/调用点计数」，所有结论均附工具原始输出；本轮 8 条测试 run 已**逐条列出并删除**（含级联 result），删除命令与输出见 `cleanup.txt`。

**残留风险 / 已知不确定项**：
1. **不可回滚的统计副作用**：`pg_stat_user_tables.strategy_run` 累计值被本轮抬高 `n_tup_upd: 357,386 → 364,041`（+6,655）、`n_tup_ins 2349→2357`、`n_tup_del 1976→1984`。**后续引用必须扣除 +6,655**。行数据已恢复（374 条 succeeded）。
2. **每帧延迟的外生性**：本轮测得 2.57–3.45 ms/帧，历史样本 0.85 ms/帧，副本 3.30 ms/帧 —— 差异归因于主机 I/O 状态，本报告**未做根因取证**（无 `wal`/`pg_stat_io` 时间序列）；故「0.85 vs 3.45」只能作为**区间**使用，禁止当固定算子。
3. **单次精确点**：长窗口协议只跑了 1 档（M5 3500 bar，Δ=1003）。另 3 档（492 / 16155 / 652 bar）因预算到点未做长窗口，其 Δ 不可用（见 `per_run_table.md` 表 A 的标注）。判词 A/B 依赖的 1003 点**已用 240 s 零漂移窗口自证**，并与 ① 的 `dur/(min(1001,bars)+2)` 常数性（三档 2.57–2.65 ms/帧）互证。
4. **累计闭合的推断成分**：1,976 条被删 run 的 bar 数不可查（§2.2 已标注为一致性推断，非直接测量）。
5. 未测 M30（P5 前 web 白名单仍为 M1/M5/M15/H1/D1；`crates/web/src/workbench.rs:148`）与 H1 大区间（不在本轮档位设计内）。
