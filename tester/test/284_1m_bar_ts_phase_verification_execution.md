## 2. 方法 A（决定性）：厂商 1m→5m 聚合恒等式

数据（同一时刻 GET `mkline?param=sh518880,m1,,1200` 与 `,m5,,400`，vol 单位=手，2026-09-15 09:50:40）：

```
厂商 m1 今日: 0930=30118 0931=55254 0932=55940 0933=28493 0934=26277 0935=43596
              0936=22586 0937=30506 0938=36230 0939=28829 0940=27048 0941=28533
              0942=21062 0943=47582 0944=36702 0945=17598 0946=13694
厂商 m5 今日: 0935=239678  0940=145199  0945=151477  0950=87198  0955=9045

m5_0940 = 145199 == Σ(m1 0936..0940) = 145199     ←「桶首对齐」Σ(m1 0935..0939)=161747 ✗
m5_0945 = 151477 == Σ(m1 0941..0945) = 151477     ←「桶首对齐」Σ(m1 0940..0944)=160927 ✗
m5_0935 = 239678 == Σ(m1 0930..0935) = 239678     ← 含 0930 行；Σ(m1 0931..0935)=209560，差额 30118 恰为 0930 行
```

**判读**：
- `m5(0940)` 恰等于厂商 m1 标号 `0936..0940` 之和 ⇒ 这些 1m 行覆盖 `[09:35,09:36) … [09:39,09:40)`，即 **`ts` = 窗口结束分钟**；
- 两处（0940、0945）全等、且桶首对齐在两处均**不**成立（差额非零且无规律）⇒ 非巧合；
- `m5(0935) = m1(0930) + Σm1(0931..0935)` ⇒ **`ts=09:30` 行是当日开盘集合竞价量**（独立于 `[09:30,09:31)` 连续竞价分钟），它被并入第一个 5m 桶 `[09:30,09:35)`；
- **附带**（供父级，超出本专项）：厂商 m5 自身是**桶尾**标注（`0940` = `[09:35,09:40)`），m15/m60 同（`1500`、`[09:30,10:30)=1030`，见 `06_*.txt`）。

## 4. 方法 C / D：已收盘交易日清单与落库旁证

### 4.1 已收盘交易日 1m 标号清单（`01_closed_day_inventory.txt`）

- 每个交易日 **n = 241 根**，首根 `09:30`、末根 `15:00`（2026-08-31 ~ 2026-09-14 共 11 个交易日全部一致）；
- **午休缺口在 `11:30 → 13:01`**（`13:00` 根不存在）；
- 末三根 `14:58`（微量或 0）→ `14:59`（**恒 v=0**，11 天全部）→ `15:00`（大额，收盘集合竞价）。

**判读（首/末根 + 集合竞价分布）**：

| 观测 | 「开始分钟」预测 | 「结束分钟」预测 | 实测 |
|------|------------------|------------------|------|
| 午休缺口 | 缺 `11:30`（`[11:30,11:31)` 休市）、有 `13:00`（`[13:00,13:01)`） | 有 `11:30`（`[11:29,11:30)`）、缺 `13:00`（`[12:59,13:00)` 休市） | **有 11:30、缺 13:00 ⇒ 结束分钟 ✅** |
| 尾盘 | `14:57`（`[14:57,14:58)`）应为静默（14:57 起集合竞价） | `14:57` = `[14:56,14:57)` 有量、`14:59` = `[14:58,14:59)` 静默、`15:00` = `[14:59,15:00)` 承接竞价撮合 | **14:57 大额、14:59=0、15:00 大额 ⇒ 结束分钟 ✅**（开始分钟下 `[14:57,14:58)` 有 2.5~4.4M 量不可能） |
| 根数 241 | 240（`09:30..11:29`+`13:00..14:59`）且无 `15:00` | 240（`09:31..11:30`+`13:01..15:00`）+ **1 根开盘竞价行 `09:30`** | **241 = 240 + 竞价行 ✅（与方法 A 的 `0930` 竞价行结论互证）** |

### 4.2 DB 旁证（`04_app_db_source_switch.txt`，只读 SQL）

- 落库标号 = 厂商标号（`crates/providers/src/tencent_ifzq.rs::parse_m1` 第 55–60 行：`col(0)` 直接 `%Y%m%d%H%M` → `cst_to_utc`，**无分钟算术**）；volume = 厂商 v(手)×100（如 09-14 `09:30` 库内 3524500 = 厂商 35245 手 ✓）；

- 09:48 起 `source` 由 `tencent_ifzq` 切为 `sina_jsonp`（换源事实，相位不变）。

**高周期原始序列的对照（顺带发现，`06_vendor_higher_period_labels.txt`）**：厂商 m5/m15/m60 **原始**序列是**桶尾**标注（今日 m5 末根 `0955` @宿主 09:50:40；09-14 first=`0935`；m60 = `1030/1130/1400/1500`）。而 app **派发**的 5m/15m/1h 为**桶首**（探针 282 桶内增长证据 + 本次实测 app-5m 今日首根标号 `09:30`，厂商 m5 今日无 `0930` 根）⇒ **app 内 1m（桶尾，厂商原样入库）与 5m/15m/1h（桶首，app 侧口径）标号相位不同**。此点属"混源/混口径"的性质，但**1m 自身在两个源之间相位一致**。

## 5. 三问逐条展开

### Q1 1m 的 `ts` 约定 = **结束分钟**（`[T−1, T)`）

- 决定性证据：方法 A（厂商 1m→5m 恒等式，两处全等）+ 方法 B（厂商与新浪两个源各一次"标号 T 的行在宿主 T−1 内累积"）；
- 支撑证据：方法 C（午休缺口 + 尾盘集合竞价分布）+ 方法 D（`ingested_at` 早于标号起点）；
- 例外与来源差异：**首根 `ts=09:30` = 开盘集合竞价行**（不是独立的一分钟窗口），而 `09:31..15:00` 均为结束分钟标注的连续竞价窗口；`tencent_ifzq` 与 `sina_jsonp` 相位**一致**（非混源不一致）。

### Q2 对 1m 卫星 LIVE 锚点的影响 = **需要 1 分钟校正**

- 现状（`design/15-multi-period/02-spec.md` §4.2）：LIVE 段 = 末根与前一根两点虚线，且该处**已显式标注"1m 相位待定，不得据此判定 1m LIVE 位置为正确"**；代码侧目前**尚无 LIVE 实现**（`grep -rn "LIVE" web/src/features/**` 仅命中测试文件），因此本结论**不构成现存缺陷**，而是**落地 LIVE 段前必须采用的锚点口径**；
- 具体要求：1m 末根 `ts` 视为**桶尾**，LIVE 段起点的真实时刻 = `ts − 60s`；若沿用 5m/15m/1h 的 `ts=桶首` 规则，则 1m 的 LIVE 末段锚点相对真实进行中窗口**右移 1 分钟**（宿主 09:48 时进行中窗口 `[09:48,09:49)` vs 末根 `ts=09:49`）。
- 5m/15m/1h：**不受影响**（探针 282 已证 `ts=桶首` 且桶内增长），本专项未推翻该结论。

### Q3 对 ④（bar 边界追加）与 dcap 1m 窗口口径的影响

- **④（每分钟兜底 `GET /api/kline`，按 `ts` 唯一键合并；`tester/report/055_*.md`/`feedRealtimePoll.test.ts` 契约）**：机制**不受破坏**——1m 标号仍整分对齐、严格单调、每分钟前移一次，末根始终是"进行中桶"（只是其 `ts` 是桶尾）。所以"边界追加/同 `ts` 覆盖"逻辑无需改动。
- **需要修正的口径（认知层面）**：
  1. 任何"用 1m 末根 `ts` 反推该 bar 的覆盖区间起点"的位置（LIVE 锚点、时间轴标注、与高周期的同刻对齐）**必须按桶尾处理**（起点 = `ts − 1min`）；
  2. 若 dcap 的 1m 窗口口径/末尾 right-edge 处理按"末根 `ts` = 当前分钟"理解（如把 `ts` 当成与宿主时钟同刻的分钟），则该 bar 恰为**同一窗口**的桶尾标号（宿主 09:51 的进行中窗口 `[09:51,09:52)` 标号为 `09:52`）⇒ 若代码用 `ts` 与宿主分钟做相等/大小比较，会出现**恒定 +1 分钟**的相位偏差；dcap 的 `closes` 数值序列本身（差分/平滑/阈值）**不受影响**，受影响的是这些点被贴到哪个时刻（以及"最新一根是否已收盘"的判定）；
  3. **交叉周期对齐**：1m 与 5m/15m/1h 的 `ts` 相位不同（1m 桶尾 vs 高周期桶首），若某处假设"同一时刻末根 1m `ts` 的分钟数应等于 5m 桶首所在分钟"则必然差 1 分钟。

## 6. 残余不确定（不臆测）

1. **竞价行归属**：`ts=09:30` 行确认是开盘集合竞价量（方法 A 恒等式），但**竞价行是否也出现在被 app 采集的 `sina_jsonp` 1m 日序列中**、以及 `sina` 在 09:30 的处理是否同构，本轮未单独验（本轮只验了 sina 09:52 一带的相位）。
2. **厂商 m1 定稿延迟**：观测到厂商在窗口结束后约 5~25s 才定稿（例：`[09:48,09:49)` 于 09:49:22 冻结）；精确分布未测（不影响相位结论）。
3. **DB 落库值可能为"首见快照"**（非最终值）：如今日 `09:46` 行库内 1587 手（厂商最终 13694 手）、`09:31` 行 1197 手（厂商最终 55254 手），而 09-14 的收盘日行则与厂商最终值全等（`09:30` 35245 ✓ / `0931` 42577 ✓ / `0943` 47582 ✓）。**这是与相位无关的另一独立现象**（疑似回填/更新策略），按规定不做因果分析，仅登记供父级裁定。
4. **app 高周期（5m/15m/1h）的具体取数端点未定位**（本次仅证明其标号口径为桶首、且与厂商 m5/m15/m60 原始桶尾序列不同）——若父级需要"④/dcap 全周期口径统一"，需另行定位其取数链路。
