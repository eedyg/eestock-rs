# ADR-025 — TimescaleDB 作业层可观测性 与 测试隔离载体治理

- 状态：**已裁决（2026-09-18）**。用户对架构师建议「全部按推荐」。
- 触发事故：**2026-09-17 03:56:20Z → 09-18 02:32Z（22.6 小时）生产 5m/15m 数据停摆、日涨跌幅昨收被冻结**
- 证据：`tester/evidence/245_tsdb_worker_slot_incident/**`（含 `EVIDENCE.md`：根因链、删前/删后、缺口量化、回填、校验）
- 关联：ADR-017（双平面部署）、ADR-019 D11（费率档案，遗留探针库来源）、**ADR-023**（30m 周期档 + cagg 刷新窗口根治；其 §6.1 第 8 条「测试隔离债」、第 12 条「测试残留进了生产 cagg」为同类问题的先例）、`design/04-storage/schema.md`（迁移与运维口径）

## 1. 事故摘要（事实，全部有原始输出）

| # | 事实 |
|---|---|
| 1 | TimescaleDB **每个装了扩展的库都会常驻一个 `Background Worker Scheduler`**，占用 PG 的 `max_worker_processes` 槽位 |
| 2 | 该实例 `max_worker_processes = 8`，而 `timescaledb.max_background_workers = 16`（**配置不一致**） |
| 3 | 带 TSDB 的库由 2 个增至 **6 个**（其中 4 个为 09-17 03:47–04:02 期间由 **ADR-023 E6b 验证车道**新建的隔离库）⇒ 常驻占用 **7/8** |
| 4 | 后果：**所有 job 无法启动**（PG 日志 `failed to launch job N … failed to start a background worker`）⇒ 生产 job 自 **09-17 03:56:20Z**（第 3 个测试库 scheduler 起来后 **2 秒**）起**连续失败 75,173 次**，17 个 job 全部逾期 |
| 5 | 用户可见症状①：5m/15m「像每 30 分钟才更新」—— 物化 watermark 冻结在 09-17 03:30Z，只剩「进行中桶」（查询期 rollup）在动；15m 与 30m 的末根逐字段相同 |
| 6 | 用户可见症状②：涨幅错误 —— `prev_close` 取 D1 昨收，而 D1 cagg 同样停摆 ⇒ 昨收冻结为半成品 **8.864**（真实 8.856）⇒ API 显示 **0.688%**，真值 **0.779%** |
| 7 | 处置：删除 5 个遗留测试库 ⇒ 槽位 7→3、6 个作业立即转 `Success`；手工 `refresh_continuous_aggregate` ×8 填平缺口（5m 09-17 行数 1100→**2200**、15m 396→**792**、昨收 8.864→**8.856**）；随后 `max_worker_processes` 提至 **32**（compose `-c`，跟既有 EV-1 参数同处） |

| # | 原因 | 证据 |

## 2. 决策

### D1 配置约束：worker 名额必须自洽（防复发，硬约束）
- 不变量：**`max_worker_processes ≥ timescaledb.max_background_workers + max_parallel_workers + 余量`**。
- 当期落地：`max_worker_processes = 32`（16 + 8 + 8），写在 `docker-compose.yml` 的 `command`（与 EV-1 参数同处，重启生效）。
- **启动自检**：app/数据面启动时校验该不等式与「带 TSDB 的库数 × 1 + 余量 ≤ max_worker_processes」，违反即**显著告警**（当前仅靠"作业失败"间接暴露，太晚）。

### D2 TimescaleDB 作业层可观测性（本 ADR 的核心新增能力）
现有观测面只覆盖 app 与数据面，**DB 作业层完全裸奔**（本次 7.5 万次失败、22.6 小时停摆，**由用户肉眼发现**）。补三个信号：

| 信号 | 口径 | 阈值（初值，可由实测调整） |
|---|---|---|
| **cagg 新鲜度** | 每个 cagg 的 `watermark`/`max(ts)` 相对 `now()` 的滞后 | 5m/15m ≤ 10 min；30m/1h ≤ 90 min；1d/1w/1mo ≤ 26 h / 8 d / 32 d |
| **job 失败率** | 滑动窗口内 `job_stats.total_failures` 增量 | 连续 ≥ 3 次失败 或 10 min 内失败率 > 50% ⇒ 告警 |
| **worker 槽位** | `pg_stat_activity` 中 `TimescaleDB%` 计数 ÷ `max_worker_processes`；带 TSDB 的库数 | 占用 ≥ 80% 或 槽位余量 ≤ 2 ⇒ 告警 |

- 落地形态：**复用既有告警通道**（`alert_rules` 表 + 告警页已存在）；采集由数据面（`eestock-data`，已持 DB 连接与 `/healthz`）承担，不新起组件。
- **判据**：任何 DB 层"数据停摆"必须能在**用户发现之前**被系统报出来；告警须带可执行定位信息（哪个 cagg / 哪个 job / 当前水位）。

### D3 测试隔离载体治理（治本）
| # | 规则 |
|---|---|
| 1 | **命名**：测试库必须 `tmp_<lane>_<yyyymmddHHMM>`（可识别、可判龄），禁止 `eestock_test` 这类无语义名长期存在 |
| 2 | **必须可销毁**：`scripts/testdb-init.sh` 增 `--drop`（teardown 路径）；**只有** teardown 完成，车道才算收尾 |
| 3 | **验收闸门用正向断言**：断言「本车道创建的载体**已不存在**」；**禁止**用「库清单无新增」代替（本次三份 db_list 逐行相同，恰恰是这个错误方向） |
| 4 | **隔离方式优先级**：**schema 级**（同库内建 schema，零 worker 槽位）＞ 独立实例 ＞ **整库**（最后手段：每库一个常驻 scheduler 槽位） |
| 5 | **清理不得置于车道最后一步**：改为"每阶段用完即清"，或脚本内 `trap … EXIT`；因车道会被 30 分钟上限截断 |
| 6 | **残留登记的语义修正**：「登记残留」**不等于**处置 —— 每条残留必须带 **owner + 到期日 + 处置动作**，缺任一项视为**未处理**（本次 294 报告「只登记、不修」即此反例） |

### D4 事故响应纪律
- DB 层/数据层事故的顺序**不可颠倒**：**先量化缺口 → 再修因 → 最后回填**。
  - 本次反面教材：`refresh policy` 窗口（5m=1h / 15m=2h）**盖不住数小时~数天缺口 ⇒ 缺口永不自动补**（与 ADR-023 §2.4 同一模式）；若只"修因"不回填，用户看到的仍是错的。
- 度量口径：缺口用**行数 + 水位**双证（`kline_5m` 09-17 = 1100 vs 应 2200）。
- 回填窗口**必须按桶边界对齐**（沿用 ADR-023 §6.1 的硬规则）。

### D5 与 ADR-023 的关系
本 ADR **不推翻** ADR-023 的任何技术决策；它补齐其 §6.1 第 8 条（测试隔离债）与第 12 条（测试残留污染生产 cagg）共同指向的**同一根因**：**测试载体没有生命周期管理**。ADR-023 §6.1 第 8 条在本 ADR 生效后视为**已升级为 D3 的强制规则**。

---

## 3. 后果

**正面**：worker 名额自洽（32 槽位 vs 当前占用 2）；DB 作业层进入观测面；测试载体有命名/销毁/正向断言三重约束；事故顺序纪律显式化。

**成本**：需实现三件事（见 §4）；`testdb-init.sh --drop` 会改变车道收尾流程（每车道多一步，但把它变成**可验证的闸门**）。

**残余风险**：
1. `max_worker_processes` 仍需重启才生效（postmaster 级）——本 ADR 不引入在线改参方案。
2. 若今后确实需要"多个独立实例"，需评估容器资源（本次为同实例多库模式）。
3. 监控阈值为初值，需按实际数据形态校准（避免误报疲劳）。
