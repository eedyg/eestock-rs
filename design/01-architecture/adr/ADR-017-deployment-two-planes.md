# ADR-017 部署双面分离（数据面 / 应用面）

- 状态：已接受（2026-09-03，用户确认）
- 修正：决策日志中「部署：Docker Compose（app+timescaledb）」的「app 单容器」表述

## 背景

Wave 0（完备产品级数据获取）启动前，用户提出：数据源相关逻辑是否应放进数据库容器。经评估三种解读（同容器多进程 / compose 独立容器 / 数据库内核内采集），确认独立容器路线，并进一步明确：**数据层是基座，应与 web/交易层故障隔离**——web server 的任何问题不得影响数据采集。

## 决策

系统拆分为**两个独立部署单元**，唯一耦合点是 TimescaleDB：

```
┌─ 数据面（基座）──────────────────────────────┐
│ eestock-data 容器                             │
│  ├─ collector：调度/熔断/当日回填/降级模式     │
│  ├─ providers：Tier1（腾讯/新浪 1m）+ 快照池  │
│  ├─ tushare：准确层日增量同步                 │
│  └─ /healthz（只读存活探测，唯一端口）        │
└──────────────────┬───────────────────────────┘
                   │ 仅通过 TimescaleDB 耦合
┌──────────────────┴───────────────────────────┐
│ eestock-app 容器（Wave 1）                    │
│  ├─ web server（REST/WS/SPA 托管）            │
│  ├─ diagnose 查询 API（读库渲染）             │
│  ├─ MCP server（ADR-009）                     │
│  └─ 交易（Wave 4，独立开关默认关）            │
└──────────────────────────────────────────────┘
```

- **无 API 直连**：两面之间禁止直接 RPC/HTTP 调用。数据出口 = kline_raw / kline_accurate / source_health_events 等表；应用面全部读库。
- **控制通道走库**：symbols 表即采集配置（scheduler 每周期重读热生效，见 03 §2）；未来的熔断手动复位等运维指令同样以 DB 标志位轮询实现。**数据面除 /healthz 外不开放任何管理端口**。
- crate 布局不变；`app` crate 提供两个 bin：`eestock-data`（Wave 0）、`eestock-app`（Wave 1）。

## 理由

- 故障隔离：web/交易层崩溃、发版、调试不影响采集连续性（用户核心诉求）。
- 单一职责与最小攻击面：数据面无 web 依赖、无入站业务流量。
- 可独立演进：数据面先行达到产品级稳定，应用面随后迭代不触碰基座。

## 被否方案

- **采集进程与 postgres 同容器**：一容器多进程反模式；生命周期耦合（DB 重启即采集中断）；healthcheck 语义混乱；安全边界消失。
- **数据库内核内采集（plpython3u/pg_cron 调外部 API）**：采集/熔断/限频逻辑沉入存储层，严重违反分层架构；untrusted 语言安全隐患；不可观测、不可测试。
- **宿主机 nohup 直跑**：进程管理裸奔、无自启、环境漂移（仅允许作为开发调试手段，非交付形态）。

## 后果

- Wave 0 必须交付 Dockerfile 与 compose `data` 服务（含 sqlx migrate 启动自检、/healthz）。
- diagnose 的「手动复位」等写操作在 Wave 1 设计时必须沿用 DB 控制通道口径，不得给数据面开管理 API。
